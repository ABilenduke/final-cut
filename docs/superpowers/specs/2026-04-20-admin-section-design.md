# Admin Section Design Spec

> **Date:** 2026-04-20 (revised 2026-04-21 — refactored to single-app architecture; admin lives inside `backend/`)
> **Status:** Approved — plan set rewritten (`docs/plans/admin/v1/00-09`)
> **Scope:** Planning only. This spec defines the architecture and plan breakdown for the admin section. Implementation happens in a later cycle, plan-by-plan.
> **Plan set:** `docs/plans/admin/v1/00-index.md`

---

## 1. Overview

Final Cut needs an admin tool so staff can manage the movie catalog, locations, auditoriums, showtimes, bookings, customers, loyalty, menu, promos, gift cards, and calendar events without shelling into `php artisan tinker`. This spec commits the architecture to **Laravel Filament 3 inside the existing `backend/` Laravel app**, served at a dedicated admin subdomain, and defines the plan breakdown, testing, and deployment shape.

The admin surface is isolated from the customer surface at three layers: a separate nginx vhost (`admin.finalcut.test` / `admin.finalcut.com`), Laravel route `domain()` constraints that prevent admin routes from answering on the customer domain and vice versa, and a separate `admin_users` table with its own auth guard and subdomain-scoped session cookie. The two surfaces share one PHP-FPM container, one codebase, and one migration history — which is the point. There is no separate Laravel app, no cross-app code bridge, no shared Composer package.

## 2. Architecture

### 2.1 Repo layout

Admin lives inside the existing backend Laravel app. No new top-level directory.

```
movie-theatre/
├── backend/            (existing Laravel API + NEW admin panel)
│   ├── app/
│   │   ├── Filament/           (NEW — Resources, Pages, Widgets)
│   │   ├── Providers/Filament/ (NEW — AdminPanelProvider.php)
│   │   ├── Models/             (existing — Movie, Booking, User, etc. shared by API + Filament)
│   │   ├── Services/           (existing + new — MovieService, ShowtimeService, etc.)
│   │   └── Http/Middleware/    (existing + new admin-guard middleware)
│   ├── database/migrations/    (existing + admin migrations: admin_users, roles, activity_log, loyalty_adjustments)
│   └── tests/Feature/Admin/    (NEW — admin-specific feature tests)
├── frontend/           (existing Nuxt customer app — unchanged)
├── nginx/
│   └── templates/conf.d/
│       ├── default.conf.template       (existing — customer + API)
│       └── admin.conf.template         (NEW — admin vhost)
├── docker-compose.yml  (unchanged — nginx already serves all vhosts, backend already runs PHP-FPM)
└── Makefile            (+admin-migrate, admin-test, admin-create-user wrapping backend artisan)
```

### 2.2 Data sharing model

One PostgreSQL database, one Laravel app. All migrations live in `backend/database/migrations/`, regardless of whether the table is consumed by the customer API, the admin panel, or both. The same `App\Models\Movie` Eloquent model backs the customer API and the Filament MovieResource. There is no model mirror, no parity test, no drift risk.

**Admin-only tables** — `admin_users`, `roles`, `permissions`, `role_has_permissions`, `model_has_roles`, `model_has_permissions`, `activity_log`, `loyalty_adjustments` — are migrated with the rest of `backend/database/migrations/`. They are distinguished from customer tables by naming and by the fact that only admin code references them (customer routes never touch `admin_users`; the admin panel never writes to customer `users` except via `LoyaltyService`).

### 2.3 Subdomain isolation & security scoping

Three layers of defense keep admin routes and customer routes from bleeding into each other's surface:

**Layer 1 — nginx vhost separation.** Two `server {}` blocks (two template files under `nginx/templates/conf.d/`): one serves `${APP_DOMAIN}` (customer site + `/api`), one serves `admin.${APP_DOMAIN}` (Filament panel only). Both fastcgi to the same backend PHP-FPM container. The admin vhost never `proxy_pass`es to the frontend Nuxt service — only PHP-FPM. The existing wildcard cert generated by `nginx/certs/generate-certs.sh` (SAN includes `*.$APP_DOMAIN`) already covers the admin subdomain; no cert regeneration required.

**Layer 2 — Laravel route domain constraints.** Customer API routes are wrapped in `Route::domain(config('app.primary_domain'))->prefix('api')->group(...)` in `backend/bootstrap/app.php`. Filament's `AdminPanelProvider` uses `->domain(config('filament.admin_domain'))`. Neither answers on the other's Host header. A Pest feature test (`RouteDomainScopingTest`) enumerates `Route::getRoutes()` and asserts every API route is bound to the primary domain, every Filament panel route is bound to the admin domain, and no route has a `null` domain constraint.

**Layer 3 — session cookie scoping.** The admin session cookie is named distinctly (`admin_session`) and scoped to `admin.${APP_DOMAIN}`. The customer session cookie (Sanctum + nuxt-auth-utils) is scoped to `${APP_DOMAIN}`. A compromised customer session cannot be replayed against the admin panel — the cookie domain does not match. Session storage is Redis with per-guard key prefixes (`admin_session:` and default).

### 2.4 Deployment topology

- Dev: `admin.finalcut.test` via second nginx vhost, self-signed TLS from the existing wildcard cert
- Prod: `admin.finalcut.com` with Let's Encrypt covering both root and admin subdomain (single cert with SAN, or two separate certs — decided in Plan 09)
- Shares the existing postgres + redis + mailpit containers
- No new PHP-FPM container, no new docker-compose service, no new migration history
- Admin subdomain can be gated behind VPN / IP allowlist in prod without affecting the customer path (allowlist block lives in `admin.conf.template`)

### 2.5 Why this works

- **One deploy pipeline.** Backend changes and admin changes ship together — they're in the same codebase and the same migration timeline. No coordination overhead.
- **No code duplication.** `MovieService`, `ShowtimeService`, `LoyaltyService` etc. live once in `backend/app/Services/` and are called by both API controllers and Filament Resources.
- **No drift risk.** There's no admin-side model mirror to keep in sync with the backend schema.
- **Customer API authorization surface doesn't grow.** Admin routes are bound to the admin domain; they don't appear in `php artisan route:list --path=api`.
- **An admin bug cannot take down ticket sales** through code isolation alone — it can through shared process crash, which matters for large synchronous admin operations. Plan 06's bulk showtime creation uses database transactions and queue-dispatched heavy work to keep the PHP-FPM workers free. Plan 09 documents the shared-pool risk and its mitigations.

### 2.6 Admin-to-domain-logic boundary

Admin Filament Resources call the same `App\Services\*` classes that the customer API calls. There is no special boundary, no shared-code package, no Causer-resolving facade layer — Filament Resources are just another client of the service layer, and service methods accept an optional `?AdminUser $actor = null` argument so `ActivityLog` can record the admin identity when writes originate from the panel.

**Rule:** Admin mutations to tables that carry invariants (bookings, loyalty, gift cards, showtime conflicts, seat availability) go through service classes in `backend/app/Services/`. Admin mutations to pure-content fields with no invariants (movie tagline, menu item description, calendar event notes) may bypass services and write directly via Eloquent. The distinction is pragmatic, not policed mechanically — if a Filament Resource's write has any chance of breaking an invariant, put it behind a service.

| Admin action | Goes through |
|---|---|
| Movie create / update / delete / enrich | `App\Services\MovieService` (created in Plan 04) |
| Showtime create / update / cancel / bulk-create | `App\Services\ShowtimeService` (created in Plan 06) |
| Seat configuration (bulk generate, edit layout) | `App\Services\AuditoriumService` (created in Plan 05) |
| Loyalty point adjustment, tier change | `App\Services\LoyaltyService` (exists — extended in Plan 07) |
| Gift card void, balance adjust | `App\Services\GiftCardService` (created in Plan 08) |
| Promo code create / deactivate | `App\Services\PromoCodeService` (created in Plan 08) |
| Menu item availability toggle | Direct Eloquent write (no invariant) |
| Calendar event CRUD | Direct Eloquent write (no invariant) |
| Movie tagline edit | Direct Eloquent write (no invariant) |

Services extracted in this planning cycle (`MovieService`, `ShowtimeService`, `AuditoriumService`, `GiftCardService`, `PromoCodeService`) live in `backend/app/Services/` alongside the existing `TmdbService`, `SeatAvailabilityService`, `StripeService`, `LoyaltyService`. The customer API moves to calling them as well where currently it uses controllers directly — that refactor is owned by each domain plan and is in-scope because the code is already in the same app.

### 2.7 Future migrations flagged (known retrofits)

Not in v1, but the design must not make these retrofits disproportionately expensive:

- **Location-scoped roles** — add `location_id` FK on `admin_users`, location-aware policies on every Resource, location filters on list pages, location scoping on seat editor / schedule planner / menu / showtimes. Design policies now so they can accept a location predicate later.
- **MFA / 2FA** — add `mfa_secret`, `mfa_enabled_at`, `recovery_codes` columns on `admin_users`; middleware between login and panel; Filament login page customization.
- **Booking write operations** (cancel, refund, seat modify) — add permissions `bookings.cancel`, `bookings.refund`, `bookings.modify`; integrate Stripe Refund API via `StripeService`; credit-memo ledger; customer-notification flow.
- **Stripe webhook integration for refund state** — currently backend confirms synchronously; booking cancellations in v2 will want webhook reconciliation.

## 3. Authentication & Authorization

### 3.1 `admin_users` table

Columns: `id, name, email (unique), password, remember_token, last_login_at, last_login_ip, disabled_at, created_at, updated_at`.

No `email_verified_at` column. Admin users are created explicitly via `admin:create-user` (no self-signup), so verification has no flow to gate. `canAccessPanel` instead checks `disabled_at IS NULL` — a real account kill switch per the project's "booleans as timestamps" convention (CLAUDE.md). Deactivating a terminated employee's account is `AdminUser::update(['disabled_at' => now()])`; reactivating is `['disabled_at' => null]`. Full migration and `canAccessPanel` implementation in Plan 02 Task 1.

No `role` column — roles live in the Spatie pivot (`model_has_roles`).

### 3.2 Auth stack

- `config/auth.php` guard: `admin` (session driver, `admin_users` provider) — added alongside the existing `web` and `sanctum` guards
- Filament Panel Provider registered at path `/` on the admin subdomain (the subdomain's entire path space is the panel)
- Filament's built-in login page — no custom auth UI work
- Session cookie `admin_session`, domain-scoped to `admin.finalcut.test` in dev and `admin.finalcut.com` in prod (no leading dot in either — cookie scoped to the exact host)
- Session driver: Redis with `admin_session:` key prefix (no collision with customer sessions)
- MFA/2FA deferred to v2 (listed in "Won't Have")

### 3.3 Roles and permissions

Uses `spatie/laravel-permission`.

| Role | Intent | Permission set |
|------|--------|----------------|
| `admin` | Full control | `*` (wildcard) |
| `manager` | Content & operations, no financial mutations | `movies.*`, `showtimes.*`, `locations.view`, `locations.update`, `auditoriums.*`, `menu.*`, `events.*`, `promos.*`, `bookings.view`, `gift_cards.view`, `users.view`, `loyalty.view` |
| `ops` | Read-only support | `bookings.view`, `users.view`, `loyalty.view`, `gift_cards.view`, `movies.view`, `showtimes.view`, `locations.view`, `auditoriums.view` |

Permissions follow `{resource}.{action}` naming where `action` is one of `view`, `create`, `update`, `delete`, or a resource-specific verb like `movies.trigger_enrich`, `loyalty.adjust_points`, `loyalty.adjust_tier`, `gift_cards.void`. Filament Resources gate themselves via policies generated from these permissions. Roles are scoped to the `admin` guard (spatie/permission `guard_name`) so the customer `users` table cannot be assigned admin roles even by accident.

**Location scoping:** none. All roles see all locations. (If future requirements demand per-location managers, we add a `location_id` to `admin_users` and location-aware policies — v2 work.)

### 3.4 Audit log

Uses `spatie/laravel-activitylog`.

- Every Filament Resource write (`create`, `update`, `delete`) logs a row in `activity_log`
- Service-level writes (`MovieService::update()`, `ShowtimeService::cancel()`, etc.) accept the optional `?AdminUser $actor = null` argument and emit activity-log entries attributed to that actor when present
- Logs capture: causer (admin_user), subject (model + id), event, before/after diff, timestamp, IP address
- Each Filament Resource has an "Activity" relation manager on its view page — admins see the history of changes to any movie, showtime, booking, etc.
- A global `/activity` page (on the admin subdomain) lists the last 30 days of activity across all resources, filterable by causer, resource type, and date range
- Retention: 180 days, pruned by a scheduled command `activity:prune --days=180` run daily

### 3.5 What admin cannot do (by design, v1)

- Log in as a customer (no access to customer `users` password hashes — separate guard, separate table, spatie/permission guard-scoped roles)
- Issue customer-facing API tokens
- Mark bookings as refunded or cancelled (permission does not exist in v1; UI hides the action)
- Bypass `TmdbService` for movie enrichment — admin triggers the existing `movies:enrich` command but does not have a direct TMDB code path

```
│
├── 04 Movie catalog
│   └── 06 Showtime management
```

### 4.3 Critical path

Minimum to have a usable admin: `01 → 02 → 03 → 04 → 05 → 06`. After Plan 06, staff can manage movies, locations, auditoriums, and showtimes — enough to run the business day-to-day. Plans 07–09 round out support, merchandise, events, and production hardening.

### 4.4 Scope boundaries

Two categories: strategic deferrals we intend to build soon, and out-of-scope indefinitely.

**Deferred but high priority post-v1:**

- **MFA / 2FA for admin login** — admin holds customer, loyalty, and gift-card access; MFA is the most obvious v1 security gap. Mitigated short-term by IP allowlist + Fail2ban, but should land as an early v2 item.
- **Booking write operations** — cancel, refund (Stripe-integrated), seat modification. Read-only in v1; manual cancellation workflow in Plan 06 documents the interim process.
- **Per-location manager scoping** — all roles see all locations in v1. Likely to be needed as the theatre operates two locations; retrofit cost is tracked in § 2.7.

**Won't have** (out of scope indefinitely, or until explicit product-driven requirement):

- Customer impersonation
- Bulk CSV import / export
- Admin-managed blog posts (blog stays in `frontend/app/data/blog.ts` until v2)
- Rate limiting beyond login endpoint (VPN / IP allowlist handles broader admin access in prod)
- Multi-tenancy / white-label support

## 5. Per-plan scope summary

One-paragraph summary per plan. Full task/acceptance-criteria detail lives inside each plan file.

### Plan 01 — Admin panel scaffold & nginx vhost

`composer require filament/filament:^3.2` inside `backend/`. Generate `backend/app/Providers/Filament/AdminPanelProvider.php` with `->domain(config('filament.admin_domain'))`, `->authGuard('admin')`, `->path('/')`. Add `nginx/templates/conf.d/admin.conf.template` as a second vhost that fastcgi-proxies to the existing backend PHP-FPM container. Wire Laravel route-domain scoping in `backend/bootstrap/app.php` so customer API routes answer only on the primary domain. Add Makefile targets (`admin-shell`, `admin-migrate`, `admin-test`, `admin-create-user`) as thin wrappers around backend artisan. Scaffold `docs/progress/admin-v1.md`. Acceptance: `https://admin.finalcut.test/login` renders Filament login; `https://finalcut.test/admin/login` returns 404; `https://admin.finalcut.test/api/movies` returns 404; Pest `RouteDomainScopingTest` passes.

### Plan 02 — Auth, roles, permissions & audit log

Create `admin_users` migration + model + factory in `backend/`. Add `admin` guard to `backend/config/auth.php`. Install `spatie/laravel-permission` and `spatie/laravel-activitylog` in `backend/composer.json`. Seed three roles (`admin`, `manager`, `ops`) with the permission sets from § 3.3, scoped to the `admin` guard. Configure the Filament panel to use the `admin` guard with subdomain-scoped session cookie. Add `admin:create-user` interactive artisan command. Add `activity:prune --days=180` command and schedule it daily. Global `/activity` page on the admin subdomain lists recent activity across all resources, filterable. Register a kill-switch middleware on the Filament panel only (not globally). Pest tests: permission gate enforcement (actingAsOps cannot write), audit log writes, role seeding idempotency, session cookie scoping, `disabled_at` blocks panel access.

### Plan 03 — Base Resource class & loyalty_adjustments table

Create `backend/app/Filament/Resources/BaseResource.php` as an abstract class that all admin Resources extend — establishes CRUD permission conventions (`getPermissionPrefix()` mapped to spatie abilities), audit-log defaults (every write emits an activity entry), and timestamp-column formatting. Create `backend/app/Filament/Concerns/FormatsCurrency.php` trait wrapping the existing frontend currency convention (cents → `$X.XX` with locale-aware formatting). Create `backend/database/migrations/*_create_loyalty_adjustments_table.php` — admin-owned table for manual loyalty point adjustments with a constrained `change_type` enum (`earn_manual`, `revoke_manual`, `tier_grant`, `tier_revoke`), causer foreign key to `admin_users`, reason string. No Resources ship in this plan — those begin in Plan 04.

### Plan 04 — Movie catalog management

Create `backend/app/Services/MovieService.php` (extracted from the existing backend movie controller logic where needed; takes optional `?AdminUser $actor` for audit attribution). Create `backend/app/Filament/Resources/MovieResource.php` with full CRUD form: title, slug, status, tmdb_id, synopsis, tagline, runtime, rating, release_date, poster/backdrop URLs, trailer key, genres multi-select, cast repeater. List page with filters (status, genre) and search. Row action: "Enrich from TMDB" dispatches the existing `movies:enrich --movie-id=X` command. Bulk action: "Mark as now_showing / coming_soon". Policy wired to `movies.*` permissions. Relation manager: upcoming showtimes for this movie (read-only preview). Pest tests: CRUD paths, enrich action dispatches the job, policy enforcement per role, activity-log entries attributed to admin causer.

### Plan 05 — Locations, auditoriums & seat editor

Create `backend/app/Services/AuditoriumService.php`. `LocationResource` (name, slug, address, phone, email, timezone, lat, lng). `AuditoriumResource` scoped to location via a relation manager on `LocationResource` — form includes name, section config (Standard / Premium / Accessible with price multipliers), and a new `cleanup_minutes` column (default 20) consumed by Plan 06 conflict detection. All writes route through `AuditoriumService`.

**Seat configuration — two-track scope:**

- **MVP (ships first, inside this plan):** a **seat-generator form** — rows count × seats-per-row + section mapping (row letters A–D = Premium, E–J = Standard, etc.) → bulk-insert `Seat` rows via `AuditoriumService::generateLayout()`. Covers ~90% of real configurations without custom UX risk. Includes an `unavailable_seats` text field (comma-separated IDs like "A3,A4") for aisle gaps.
- **Visual editor (ships after MVP, still inside this plan if budget allows; otherwise deferred to a follow-up):** custom Filament page at `backend/app/Filament/Pages/SeatEditor.php` rendering the auditorium grid, click-to-toggle seat type, drag-select bulk operations. Built on top of the MVP data model so the fallback is never wasted work.

Pest tests: generator correctness, section pricing math, unavailable-seat masking, `AuditoriumService` call path, policy enforcement. Visual editor tests gated on whether it ships in this plan vs later.

### Plan 06 — Showtime management

Create `backend/app/Services/ShowtimeService.php`. `ShowtimeResource` with form (movie select, location + auditorium cascade, start_time, price_standard / premium / accessible in cents). All mutations route through `ShowtimeService`. Conflict detection validates `end_time = start_time + movie.runtime + auditorium.cleanup_minutes` and blocks overlaps in the same auditorium. Bulk create: "Add this movie to Auditorium 1, Monday–Friday, 7pm and 9:30pm for two weeks" — calls `ShowtimeService::bulkCreate()`.

**Schedule UX — two-track scope:**

- **MVP (ships first):** standard Filament table list with date-range filter + auditorium filter, plus the bulk-create dialog. Conflict validation runs server-side. Calendar view not required for initial usability.
- **Visual schedule planner (optional second pass):** custom Filament page with per-auditorium weekly calendar, drag-to-create, click-to-edit. Built on the same service, so the MVP is forward-compatible.

**Cancellation workflow** (v1, no automatic refund):

1. "Cancel showtime" action soft-deletes the `showtimes` row via `ShowtimeService::cancel()`.
2. Every affected `booking` row gets `flagged_at = now()` set (new column, Plan 06 adds the migration) and a reason string `"showtime_cancelled:{showtime_id}"`.
3. Activity log writes one entry per cancellation plus one per flagged booking.
4. A queued job dispatches a **stubbed email** (Mailpit in dev, real SMTP in prod) to each affected customer: "Your showtime was cancelled. Staff will contact you about a refund." Template lives in `backend/resources/views/mail/showtime-cancelled.blade.php`.
5. Admin gets a new page at `/cancelled-showtime-followup` — lists every booking with `flagged_at IS NOT NULL AND status != 'refunded'`. This is the manual finance queue; staff work through it out-of-band until Stripe refund integration lands in v2.
6. Seats from cancelled showtimes are *not* auto-released; the soft-deleted showtime is filtered from all customer queries, so seats are effectively dead.

Pest tests: conflict detection with per-auditorium buffer, `bulkCreate` service call path, cancellation writes flag + activity entries, follow-up page shows only pending bookings, email job dispatched per booking.

### Plan 07 — Bookings, customers & loyalty

`BookingResource` is **read-only** — lookup by confirmation code, email, or showtime. View page shows seats, food items, payment breakdown, Stripe PaymentIntent ID, customer, linked showtime. Full-text search across email + confirmation code. `UserResource` (customer users, read-only except tier + points). Loyalty actions use the existing `backend/app/Services/LoyaltyService.php`, extended with methods like `adjustPoints(?AdminUser $actor, User $user, int $delta, string $reason)` and `grantPremier(?AdminUser $actor, User $user, Carbon $expiry)`. Writes land in the `loyalty_adjustments` table plus an activity-log entry. `loyalty_adjustments` table (from Plan 03) tracks manual adjustments separately from earned/redeemed ledger. Pest tests: search, policy enforcement, loyalty math, adjustment attribution, activity-log entries.

### Plan 08 — Menu, promo codes & gift cards

Create `backend/app/Services/GiftCardService.php` and `backend/app/Services/PromoCodeService.php`. `MenuItemResource` scoped per-location (category, allergens, dietary tags, price in cents, image, availability toggle) — direct Eloquent writes permitted. `PromoCodeResource` (code, discount_type enum, amount, usage limit, expires_at, active) — all writes route through `PromoCodeService`. `GiftCardResource` is read-focused — list all, search by code / recipient, view balance history. Single write action: "Void gift card" sets `status=voided` via `GiftCardService::void(?AdminUser $actor, GiftCard $card, string $reason)`, logs reason, and alerts finance via email stub. Pest tests: per-location menu scoping, promo validation, gift card void audit trail, service-layer causer attribution.

### Plan 09 — Calendar events, testing & hardening

`CalendarEventResource` (title, slug, type, date, start / end time, description, image, loyalty_only flag, accessibility tags, ticket URL). Full admin Pest suite pass — every Resource has CRUD + policy tests under `backend/tests/Feature/Admin/`. Production hardening: nginx `allow <VPN CIDR>; deny all;` block in `admin.conf.template` activated in prod via an `envsubst`-rendered include, Fail2ban jail parsing the admin nginx access log for `/login` failures (5 failures in 10 minutes = 24-hour ban), Laravel `throttle:admin-login` rate limit (5 req/min per IP) on the admin login route. CI: admin tests run inside the existing `make test-backend` target — no separate admin job. Docs: update root `CLAUDE.md` with admin commands and the subdomain, update `docs/README.md` entry for admin, update `docs/architecture/SITE_ARCHITECTURE.md` to document the admin panel's placement.

## 6. Testing

Pest, matching backend. All admin tests live inside `backend/tests/`.

### 6.1 Test layout

- `backend/tests/Feature/Admin/` — Filament Resource tests using `livewire/livewire` helpers (`Livewire::test(ListMovies::class)`). Covers CRUD paths, policy enforcement, form validation, relation managers, custom pages (seat editor, schedule planner, cancelled-showtime-followup).
- `backend/tests/Unit/Admin/` — admin-specific services, policies, activity log formatters, BaseResource concerns.
- `backend/tests/Helpers/AdminAuthHelper.php` — trait exposing `actingAsAdmin()`, `actingAsManager()`, `actingAsOps()`, `actingAsNobody()`. Mirrors the backend's `AuthHelper` pattern.
- No separate `phpunit.xml` — the existing `backend/phpunit.xml` covers admin tests too.

### 6.2 Route-domain scoping test

`backend/tests/Feature/RouteDomainScopingTest.php` enumerates `Route::getRoutes()` and asserts:

- Every route with path prefix `api/` has `domain === config('app.primary_domain')`
- Every route registered by Filament's `AdminPanelProvider` has `domain === config('filament.admin_domain')`
- No route has `domain === null`

This is the primary security-scoping guardrail. It catches the case where someone later adds an API endpoint outside the `Route::domain()` group — the test fails before the change merges.

### 6.3 What we do not test

- Filament's own form-builder internals (trust the framework)
- Livewire's session / render lifecycle (trust the framework)
- Spatie Permission's pivot math (trust the package)

We test our configuration, policies, custom actions, services, route-domain scoping, and the activity-log attribution chain.

## 7. Deployment

### 7.1 Infrastructure

- Production vhost `admin.finalcut.com` added via a second `server {}` block in the production nginx config (same template-rendering mechanism as dev)
- Let's Encrypt cert covers both `finalcut.com` and `admin.finalcut.com` (single cert with SAN, or two separate certs — decision in Plan 09 based on certbot ergonomics)
- IP allowlist block in `admin.conf.template` — env-driven CIDR list, empty in dev (disabled by default), populated in prod
- Fail2ban jail parsing the admin nginx access log for `/login` 4xx responses: 5 failed logins in 10 minutes = 24-hour ban
- Rate limit: `/login` on the admin domain capped at 5 req/min per IP via Laravel `throttle:admin-login` middleware registered in the `AdminPanelProvider`
- Session encryption: `SESSION_ENCRYPT=true`, session driver `redis` with prefix `admin_session:`
- Same `APP_KEY` as backend (single app, single key)

### 7.2 Make targets

```
admin-migrate             # Run admin-related migrations (same as make migrate — one Laravel app, one migration history)
```

## 9. Refactor note

This spec was rewritten on 2026-04-21 to replace the previously-planned two-Laravel-app architecture with a single-app architecture. The previous version assumed admin would live in a new top-level `admin/` directory with its own Docker service, a `packages/shared-domain/` Composer package bridging the two apps, a mirror of Eloquent models, a `ModelParityTest` tripwire, and phpstan + deptrac rules policing a write boundary. All of that complexity was load-bearing only because of the two-app split — with one app, it evaporates.

The security arguments the two-app split was making (subdomain isolation, separate session cookie, IP-allowlistable surface, no admin routes on the customer domain) are preserved verbatim by the three-layer scoping defined in § 2.3: nginx vhost separation, Laravel route-domain constraints, and cookie scoping. The plan set reflects the new architecture.
